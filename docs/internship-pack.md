## 二、面试自述话术（执行导向版）

### 2.1 开场自述（30–60 秒）

> "我目前在为游戏测试方向准备一个**可复现的作品集**：自研塔防数值引擎 + 一整套测试体系。
> 如果现在把我放到一个真实项目里，我的第一周会这样过：先把环境和回归基线跑通 →
> 按优先级执行用例 → 把发现的问题按『影响面 + 复现步骤 + 建议』结构化上报 →
> 用跑出的数据给开发提一两条可执行的调优建议。这套动作我在自己的项目里已经完整跑过：
> 79 条用例全绿、抓出并协助修复 3 个缺陷、用 200 万抽和 3600 局模拟产出过给
> 数值策划的结论。我既能踏实执行，也能在熟悉之后主动提出改进。"

要点：第一句是"我能执行"，第二句给证据，第三句表态"踏实 + 主动"，全程不堆体系词。

### 2.2 实习高频追问与快答（口述版）

**Q1 拿到一个真实测试任务，你怎么开始？**
> "五步：① 先找需求/验收标准，把范围与优先级定下来（没有文档就先问）；
> ② 搭可复现环境——固定 seed、固定版本，保证问题能复现；
> ③ 冒烟 + 主流程先过，再补边界和异常；
> ④ 回归并记录结果；⑤ 把发现按结构化格式上报，并附上建议。
> 我项目里的需求说明书和用例矩阵就是按这套流程做的。"

**Q2 你的用例是怎么设计出来的？**
> "先有需求条目，再为每条需求**手算黄金样本**再写断言——期望值来自需求文档而不是实现。
> 比如物理伤害 `max(atk−def, ⌈atk×5%⌉)`，我先手算 atk95 vs def100 应该是 5，
> 再写成用例；这样测试才能抓实现错误。79 条用例和 13 个需求域的对应关系我做了
> 追踪矩阵，面试官可以随便抽查一条。"

**Q3 发现一个 bug，你会怎么上报？**
> "我会用固定结构：标题一句话 / 环境与版本 / 复现步骤 / 期望 vs 实际 / 影响面与严重度 /
> 初步定位 / 建议。举个例子：我在平衡测试里把干员攻击砍了 30%，三星率从 100% 掉到
> 43%——我不会只说『坏了』，而是附上区间建议：至少恢复到原值 79% 以上（atk≥109），
> 开发照这个改完回归就绿了。"

**Q4 用例跑挂了、或者复现不出来怎么办？**
> "先分三类看：是环境问题、用例问题、还是产品问题。环境问题先固定 seed/版本重跑；
> 用例问题检查断言期望值是否合理（我对过黄金样本就不会拍脑袋）；确属产品问题就按
> Q3 的格式上报。我的模拟全是 seed 固定可复现的，就是为了让『复现不了』不发生。"

**Q5 怎么跟开发/策划提建议又不显得外行？**
> "原则：**数据说话、给区间不给结论**。我会把 SQL 或模拟的统计结果带上，说
> 『现在带真伤编队 0 漏怪、不带真伤平均漏 1.7 只/局，是否考虑上调物伤干员或下调
> 该关防御？』而不是直接说『这关数值有问题』。给对方决策空间。"

**Q6 为什么想做游戏测试？你玩游戏吗？**
> "我是塔防品类玩家（也玩明日方舟），以前是『玩家吐槽数值』，现在是想用测试和数学
> 验证数值——所以我选了塔防做可测对象，把伤害公式、保底、克制这些设计手法搬进引擎
> 验证。丰富经验 + 测试视角是我选这个方向的原因。"

**Q7 你能实习多久、每周几天？** → 如实回答（投递前先想清楚）。

**Q8 你测的是自己写的引擎，放到真实游戏行吗？**
> "我承认差异：引擎验证的是数值与规则层，真实项目还有表现层、服务器、埋点。但方法论
> 是一致的——真实游戏我会优先做三件事：核心循环的数值结算与状态机黄金样本、配置数据
> 链路审计、回归基线建立；再按需求文档驱动测试。这也是我学这套方法的目的：迁移到真实管线。"

## 三、项目深度讲解（给自己"讲熟"用）

### 3.1 一句话与定位

**MiniTower QA**：自研轻量塔防数值引擎 + 覆盖 功能/数值/概率/性能/数据/AI 的质量保障体系。
它是"被测对象 + 测试方"合一的作品集：既能演示需求→用例→自动化的工程能力，
也能演示 数值测试/概率假设检验/数据反哺/AI 防幻觉 这些游戏测试岗的稀缺能力。

### 3.2 全景结构

```
mini-tower-qa/
├─ mini_tower/       被测对象 SUT（纯 Python、零第三方运行时依赖）
│  ├─ models.py       数据模型：干员/敌人/关卡/招募池（逻辑与数据分离）
│  ├─ loader.py       JSON 加载+域校验：坏配置在加载期拒绝（测试左移）
│  ├─ combat.py       战斗引擎：时间轴模拟（伤害/技能/索敌/波次/三星/超时守卫）
│  ├─ simulator.py    单局/批量模拟 + 干员伤害占比聚合（蒙特卡洛底座）
│  ├─ recruit.py      招募概率：基础率/软保底/硬保底（seed 可复现）
│  ├─ stats.py        统计工具：χ² 拟合优度、二项置信区间（纯 stdlib）
│  ├─ analysis.py     理论 DPS/膨胀比/克制比静态校验
│  ├─ db.py           SQLite 落库（sim_runs / recruit_runs）
│  ├─ perf.py         性能基准/伸缩曲线/基线比对
│  ├─ ai.py           AI 三条线 + 三道闸（schema/引擎交叉验证/审计）
│  └─ data/*.json     全部数值配置（改一行 = 一次数值改动）
├─ tests/            79 条用例（smoke12/规则20/概率10/平衡10/数据6/性能6/调参4/AI11）
├─ sql/analysis.sql   6 条分析 SQL（Q1~Q6）
├─ scripts/           报告/演示脚本（w3_report/w4_bench/w4_tune_demo/w5_ai_demo/ci_daily_balance/export_allure）
├─ docs/              需求说明书/用例矩阵/缺陷复盘/各周报告/审查报告/面试工具包
└─ .github/workflows/ 提交 + 每日 02:00 UTC 全量回归 + 平衡漂移检测（摘要进 Job Summary、产物归档）
```

### 3.3 六个里程碑（按周，全部有真实产出）

| 周 | 做了什么 | 可展示证据 |
|---|---|---|
| W1 | 需求条目化 + 引擎核心 + 确定性 | 需求说明书；真实缺陷 BUG-001 修复 |
| W2 | 规则/边界用例矩阵 20 条 | 黄金样本测试；BUG-002/003 复盘 |
| W3 | 数值三件套 + SQLite | 200 万抽 χ²=0.146；3600 局 6 条 SQL |
| W4 | 性能 + 调参故事线 | 0.09ms/局、伸缩比 9.9；atk≥109 闭环 |
| W5 | AI 三道闸 + CI | AI 建议 100 被实测 109 驳回的防幻觉演示 |
| W6 | Allure + 面试包 + 审查 | allure-report 79/79；jd-review 逐条对照 |

### 3.4 五个必讲透的机制（面试深挖点）

1. **确定性**：所有随机源只有暴击判定且受 seed 控制 → 统计结论可复现；这是整套数值
   测试可信的地基。复现命令：seed 相同两次跑，事件逐条一致。
2. **黄金样本**：期望值=需求手算，非实现抄写 → 测试独立于实现，才能抓 BUG-002/003。
3. **数据反哺**：测试不是终点，SQLite+SQL 把 3600 局变成可查询的决策依据（Q2 高防关
   结论）；"测试产出→数据→建议"闭环。
4. **调参故事线**：改数值→红→二分给区间→绿，演示"发现问题+给出可执行解决方案"。
5. **AI 防幻觉三道闸**：schema 校验 / 引擎实测交叉验证 / 人工审计——多数人拿 AI
   结论直接用，我做的是"AI 初稿 + 可验证闭环"。

### 3.5 面试当天 10 分钟自证流程

```powershell
cd mini-tower-qa                                      # 进入仓库根目录
python -m mini_tower                                  # 1) 引擎演示（30 秒）
python -m unittest discover -s tests                  # 2) 79 条全绿（5 秒）
python scripts/w4_tune_demo.py                        # 3) 调参故事线（红→建议→绿）
python scripts/w5_ai_demo.py                          # 4) AI 三道闸 + 审计
python scripts/ci_daily_balance.py                    # 5) 平衡回归/漂移检测
# 打开 allure-report/index.html（用 HTTP，勿用 file://） 6) 报告按 epic→feature 钻取
```

### 3.6 数字速查卡（被追问脱口而出）

| 问题 | 答案 |
|---|---|
| 多少用例/通过 | 79 / 79 全绿（5 秒跑完） |
| 概率怎么验的 | 200 万抽：χ²=0.146<5.991(df=2)；6★ 率 2.003% 在 95% CI 内含声明 2% |
| 保底怎么验的 | 整体率 2%→2.89%；任意连续窗口 6★ 间隔 ≤100 |
| 性能多少 | 1-1 单局 0.092ms、峰值内存 9KB；×10 敌人耗时 ×9.3~9.9 |
| 调参结论 | 砍 30% → 三星 100%→43%；建议 atk≥109（≈原值 77%）；采纳 112 → 100% |
| SQL 结论 | 1-2 带真伤 0 漏怪 vs 不带真伤漏 1200/1400；最强编队漂移每日检测 |
| 缺陷几个 | 3 个（1 真实 BUG-001 + 2 演练 BUG-002/003），均有红→修→回归记录 |

### 3.7 诚实边界（主动讲，加分）

- **演练 vs 真实**：BUG-002/003 是按方法论做的受控演练（演示完整闭环），BUG-001 是
  演示中真实触发；会主动说明，不冒充。
- **自研 vs 真实管线**：引擎验证数值层；真实游戏的方法论迁移见 Q8 话术。
- **单人项目**：协作/沟通证据靠开源支线或面试行为题补（计划已写进方案 §2.5）。
